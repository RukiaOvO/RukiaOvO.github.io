### 正式域名必须先纠正的假设

`rukiaovo.github.io` 是 GitHub 提供的 Pages 子域名，不是用户可将 DNS 指向 Vercel 的自有域名。保留文章的 `/posts/[slug]/` 路径与保留原始 hostname 是两件事。

推荐方案：采用自有域名承载 Vercel 站点，在确认解析、证书和应用配置后，设计 GitHub Pages 旧站的过渡链接或受平台能力约束的跳转。GitHub Pages 不能承诺任意服务端 301 规则，具体旧站迁移方式必须实测。

备选方案：用稳定的 Vercel 域名发布，同时保留旧站作为过渡入口。若必须始终使用原 `github.io` 地址，则要重新评估托管方案；Next.js 静态导出不支持当前计划的同站 Route Handlers，不能直接当作等价替代。

正式域名确定前，现有 `SITE_URL` 只是兼容占位，不应视为已批准的 Vercel 生产地址。域名变化还需同步核对 OAuth 来源、Giscus 关联和旧站索引策略。

## 4. 分批修复与实施顺序

### 批次 A：先补本地缺陷与验收基础

- 范围：F01、F02、F03、F04；补充超过一页的内容夹具、代码复制交互、完整目录跳转和 Preview 索引规则自动检查。

- 产出：修复代码、对应回归、更新后的兼容清单；完成后执行 lint、类型、必要单测、生产构建和相关浏览器测试。
- 退出条件：旧标签二次提交不丢筛选；资源同步不会残留或误删；测试不被正常发文/换域名破坏；目录 id 与文内链接一致。

### 批次 B：天气作为第一条完整实时链路

- 前置：已有城市配置，可立即开始；上线级共享限流所需资源归入 D05。
- 实现 `/api/weather/`：只接受配置内城市标识，校验第三方响应，增加有界超时、缓存及统一错误响应；接口不接受任意上游 URL。
- 接入天气卡片：城市切换、加载/空/错误/超时、重试、取消旧请求，避免切换城市后旧响应覆盖新结果。
- 建立共享 API 工具：建议成功响应包含 `data`、`updatedAt`、`stale`，失败包含稳定错误码、可读提示、是否可重试及请求标识；日志不输出凭据。
- 退出条件：真实城市数据可用；模拟失败/超时/非法响应和快速切换均通过；并发请求及缓存行为有证据。共享限流尚未接入时只能记为开发完成，不能宣告生产闭环。

### 批次 C：Worker 兼容与动态页面

- 前置：D02 各接口的契约分别确认；无需等待所有接口同时就绪。
- 顺序：GitHub 事件 → RSS 聚合 → Steam 状态/最近游戏 → 访客。访客放最后，先确认读取是否写计数、会话去重和原始存储。
- 实现目标 Route Handlers：`/api/github/events/`、`/api/rss/`、`/api/steam/status/`、`/api/steam/games/`、`/api/visitor/`。
- 第一版优先代理现有 Worker；若选择独立 GitHub/RSS 上游，先记录新接口契约及回退规则，不删除旧 Worker 路径。
- 动态页面完成真实事件流、RSS 分类、分页、时间排序、链接去重、来源状态；首页接入对应卡片和近期活动。
- 访客接口明确禁止构建预取、链接预取或通用重试造成重复计数；没有确认语义前不对真实计数端点进行压力/故障测试。
- 退出条件：每个接口的成功/空/失败/超时均验收；部分源故障可降级；访客累计值保持且刷新/重试行为符合契约。

### 批次 D：缓存、限流与 Cron 运行闭环

- 前置：D05 存储与 Vercel 配额选定。共享基础可随 B/C 逐步接入，不必等界面全部完成。
- 按接口设置 TTL、过期数据回退、刷新策略；状态数据与访客累计采用不同存储/缓存规则。
- 设置多实例可用的限流、稳定 429 和 Retry-After；记录请求 ID、上游状态、耗时、缓存命中和刷新失败。
- 只为有明确刷新收益的数据设置 Cron（如 RSS）；使用鉴权、幂等和并发保护。按实际套餐限制选择频率，不预设不可用的调度计划。
- 退出条件：缓存过期/故障、多实例限流、未授权 Cron、重复触发和刷新失败场景均通过；有可查询日志。

### 批次 E：线上 Preview 与 CMS/评论联调

- 可先创建静态 Preview 完成基础部署验证，完整退出依赖 B/C/D 的功能完成及 D01 的目标域名决定。
- 将待发布代码整理为可审查提交；关联 Vercel Git 集成，配置 Preview/Production 环境，获取 CI 与部署记录。
- CMS 用隔离分支/仓库联调，特别检查现配置 `branch: main`，避免从 Preview 直接发布生产；真实 OAuth 和用户操作需账户参与。

- 完成关于/项目范围对应的入口及展示；若范围调整则同步需求基线，不能静默漏项。
- 退出条件：Preview 端到端发布链路、真实评论与实时服务均有证据；页面无域名/资源/索引配置串用。

### 批次 F：发布验收、切换与回滚

- 前置：D01–D10 的首版要求和 F01–F04 完成或经明确范围调整；所有 P0 关闭。
- 执行第 5 节验收，记录提交 SHA、Preview URL、检查结果及残余限制。
- 准备旧站过渡、目标域名、证书、canonical、sitemap、OAuth/Giscus 来源，以及原 Hugo 部署的保留/退出步骤。
- 在具体发布方案和回滚方案可审查后安排生产切换；切换后复查关键页面、API、CMS 和评论。
- 退出条件：目标域名线上可用、旧链接过渡符合约定、生产构建/探测通过、出现问题可恢复前一版本。此时才将重写首版标记完成。

## 6. 推荐下一步

先执行批次 A 的代码修复，随后完成批次 B 天气链路。同时准备正式域名决定、Worker 契约和 Vercel/OAuth 资源。这样缺少 Worker 源码不会阻塞可独立完成的工作。
